The multi-module reactor under /app is mid-cutover onto a new BOM and JDK module path. Classpath-oriented compiles of individual modules can still look fine, but ship and field packaging lanes do not both produce a coherent modular runtime, packaged jars omit processor-generated classes that downstream modules need, and the ModuleLayer launcher fails to resolve the automatic modules the cutover expects.

Ops notes under /app/ops describe the intended ship and field module rosters. Hook tag material lives under /app/link. Bring the reactor to a state where `mvn -o -Pship -q -DskipTests package` and `mvn -o -Pfield -q -DskipTests package` both succeed, the ship launcher writes /output/module-roster.json listing ship modules with status active (including the ship-only automatic module) while a field launch marks that ship-only automatic module inactive and the field automatic module active, a default launch does not mark both automatic modules active, and the packaged core jar contains the generated binding class and hook tag string documented under /app/link.
