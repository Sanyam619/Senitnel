Our stor-7 node died partway through a background compaction and took its root disk with it. All we salvaged is the data volume, mounted at /app/data: column stripes under /app/data/columns/, manifest journal tiers under /app/data/manifests/, WAL segments under /app/data/wal/, plus the node's sidecar caches and boot snapshot. The store binary is gone, so the recovery view has to be rebuilt directly from those files. The storage team's format notes are under /app/docs/. Everything under /app/data is evidence — leave it byte-for-byte unchanged.

Rebuild the newest consistent point-in-time view: the highest journal generation whose resolved stripe set verifies for every namespace, with the acknowledged WAL changes applied on top of it. Write one view file per namespace to /output/view/events.tsv and /output/view/metrics.tsv — one line per live key in the form key<TAB>value<TAB>timestamp, sorted ascending by key bytes, LF endings, no header.

Summarize the rewind in /output/rewind-report.json with these fields: restored_generation (the generation the views were rebuilt at) and checkpoint_seq (sequence of the newest WAL checkpoint); a wal object with durable_ops and rewound_ops counting distinct acknowledged vs unacknowledged put/delete operations (checkpoint markers and any incomplete trailing record count as neither); and a namespaces object with an entry per namespace carrying visible_stripes (stripe count of the manifest entry the view used), live_keys (rows in its view file), removed_keys (keys that held a value in the restored base or through an acknowledged write yet are absent from the view), value_total (sum of the view's values), and view_digest (lowercase SHA-256 hex of that view file's exact bytes).
